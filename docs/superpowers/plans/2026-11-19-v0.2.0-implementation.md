# v0.2.0 六项体验改进 实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 交付 v0.2.0：标签栏右键菜单、项目网格滚动提示、任务列表环境筛选、单次/收藏部署的构建成功自动上线、收藏备注与彩色标签、Monaco 日志渲染。

**Architecture:** 六个互相独立的改动按 P1→P6 顺序落地，每个任务自带测试闭环。写操作一律经 Pinia store（视图不直接调写接口）；Rust 侧只加数据字段与两条 IPC 组（收藏元数据 + 标签注册表），不碰业务语义；日志改为纯函数 `planModelSync` 驱动的 Monaco 增量同步，实时日志与历史预览共用 `LogEditor`。

**Tech Stack:** Vue 3 + TypeScript + Vite + Pinia + Tailwind + shadcn-vue(ui 包装) + reka-ui + Tauri 2 + Rust + Vitest(jsdom) + monaco-editor。

**Spec:** `docs/superpowers/specs/2026-11-19-v0.2.0-design.md`

## Global Constraints

- 版本已是 `0.2.0`（`package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml`、`src-tauri/Cargo.lock` 的 `zz-deploy-desktop` 条目）。
- 除 `monaco-editor` 外不新增依赖；右键菜单用现有 `reka-ui`。
- 分层不变：`api/*` 只做 IPC/HTTP，写操作经 store，视图不直接调 `saveFavorite` 等写接口。
- 注释用中文、解释"为什么"，不复述代码；测试文件与被测文件同目录同前缀。
- 测试命令：前端 `npm test -- <路径>`（vitest run），Rust `cd src-tauri && cargo test <过滤词>`。
- 单次/收藏部署的「自动上线」默认关、不持久化、不写进收藏。
- 未知标签一律前端兜底灰色；颜色只接受 `#RRGGBB`。
- 每个任务结束跑该任务的测试命令并提交一次。

## Review Focus

1. **日志在"构建已结束才打开标签/历史回放"时的行同步**：服务端重放全量快照后不再有增量，若同步逻辑把 pending 当新行，会多出一行或丢最后一行 → Task 13/16 的用例。
2. **右键菜单动作与标签生命周期竞态**：菜单打开后目标标签已被其它操作关掉，关闭其它/右侧不能误关别的或抛错 → Task 2 的用例。
3. **环境筛选下的翻页**：服务端分页链接不带 `env`，翻页后必须仍带筛选条件 → Task 4/5 的用例。
4. **收藏被向导"重新收藏"覆盖**：同项目/环境/类型/分支再次保存时备注与标签必须保留 → Task 9 的 Rust 用例。
5. **Monaco 标签从隐藏变可见**：后台收到大量日志后切回，布局为 0 时必须 `layout()` 再滚到底 → Task 15/16 的用例。

### Task 16: `planModelSync`（纯函数同步规划）

**Files:**
- Create: `src/lib/logModel.ts`
- Test: `src/lib/logModel.test.ts`

**Interfaces:**
- Consumes: `LogLine`（`@/lib/ansi`：`{ id: number; text: string; updates: number }`）。
- Produces:
  ```ts
  export interface SyncState { lastId: number; dropped: number; pending: string; texts: Map<number, string> }
  export interface SyncInput { lines: LogLine[]; dropped: number; pending: string }
  /** startLine/endLine 为 0 基、end 不含；start===end 表示纯插入 */
  export interface ModelEdit { startLine: number; endLine: number; text: string }
  export type SyncPlan = { mode: "edits"; edits: ModelEdit[]; state: SyncState } | { mode: "reset"; text: string; state: SyncState }
  export function planModelSync(prev: SyncState | null, next: SyncInput): SyncPlan
  export function fullText(lines: LogLine[], pending: string): string
  ```
  规则（对应设计 §3）：
  - `prev === null`、`next.lines` 为空、`next.dropped < prev.dropped`、或 `prev.lastId` 不在 `lines` 里 → `reset`（text = 全部行 + pending，行间 `\n`）。
  - `next.dropped > prev.dropped` → 先删模型开头 `delta = next.dropped - prev.dropped` 行（`{startLine:0,endLine:delta,text:""}`）。
  - `id <= prev.lastId` 且文本与 `texts` 不一致的尾部行（只看最后 500 行）→ 逐行 replace（`{startLine:i,endLine:i+1,text}`）；不一致行数 > 50 → `reset`。
  - `id > prev.lastId` → 末尾一次插入。
  - pending 行始终是模型最后一行：内容变化 → replace 最后一行；pending 变空且模型有 pending 行 → 删除该行。模型行号计算时把 pending 行算在内。

- [ ] **Step 1: 写失败测试**（`src/lib/logModel.test.ts`，9 条）
  1. 首次同步：3 行 + pending → `reset`，text 为 4 行。
  2. 纯追加：`lastId=3`，新增 id 4、5 → 一条 edit 追加两行，`startLine===endLine===3`。
  3. 头部丢行：`dropped 0→2` → 第一条 edit 删前两行，随后追加新行。
  4. 进度行原地改写：id 3 文本变了（`updates=2`）→ 一条 replace `{startLine:2,endLine:3}`。
  5. 改写过多（60 行）→ `reset`。
  6. 清空（`lines: []`）→ `reset` 且 `text === ""`。
  7. 服务端 reset：`dropped` 从 5 变 0 → `reset`。
  8. pending 变空 → 删除最后一行；pending 内容变化 → replace 最后一行。
  9. pending 存在时追加：新增行插在 pending 之前（`startLine` = 已落地行数）。
