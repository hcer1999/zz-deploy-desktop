## Task 1: 只通知「我自己提交」的构建（bug）

**问题复现**：`useBuildNotifications` 只做「构建中 → 终态」的状态跃迁 diff，不看提交人；而任务列表是**全员**的，所以同事提交的构建也会弹给我。

**关键发现**：服务端页面左侧导航栏里带着当前登录人的**显示名**：

```html
<div class="dropdown profile-element">
  <span><img src="/static/img/..._hehaocheng.png" /></span>
  <strong class="font-bold">贺浩成  <span style="color: #8095a8"></span></strong>
```

而「提交人」列（`鲁佩` / `彭威`）是**同一套名字**。注意它**不是**登录账号——账号是拼音（`hehaocheng`），拿账号去比会永远不匹配。四个 fixture 里这个节点都在。

- [x] **Step 1: parser 解析当前登录人**

```ts
// src/api/parser.ts
export interface TaskListResult {
  tasks: DeployTask[];
  pageInfo: PageInfo;
  currentUser: string;   // 解析不到时空串
}

function parseCurrentUser($): string {
  return $("div.profile-element strong.font-bold").first().text().trim();
}
```

- [x] **Step 2: store 回填（空值不覆盖）**

`stores/tasks.ts` 增 `currentUser`，`refresh()` 里 `if (r.currentUser) currentUser.value = r.currentUser;` —— 个别页面若缺导航栏，别把已经学到的身份清掉。

- [x] **Step 3: 通知里加过滤**

```ts
function isMine(t: DeployTask): boolean {
  const me = tasks.currentUser.trim();
  return me !== "" && t.submitter.trim() === me;
}

function notifyOnce(t: DeployTask, state: BuildResult): void {
  if (!isMine(t)) return;   // 身份未知时同样返回 false → 不弹
  ...
}
```

放在 `notifyOnce` 里，**两个触发点（日志流结束、轮询状态跃迁）自动都覆盖**；且不写进去重集合，将来身份学到后再跃迁仍能通知。

- [x] **Step 4: 测试**

`useBuildNotifications.test.ts`：`beforeEach` 里设 `currentUser = "zhangsan"`；新增「别人提交的不通知」「同一批里只有自己那条弹」「身份未知时不通知」。`parser.test.ts` 断言 fixture 解析出 `贺浩成`，且**不含**拼音账号；`tasks.test.ts` 断言空值不覆盖。

## Task 4: 修复「日志标签不自动滚动」（用户实报）

**现象**：任务列表点「Log」后，日志不跟着滚。

**结论：WebSocket 与自动滚动都是好的，坏的是「标签不在前台」这个情形。**
用真实 Chromium + 真实 Vue 组件 + 真实 Tailwind 布局做了一次复现（Vite 起一个临时入口，
用 `window.__TAURI_INTERNALS__` 桩把 `log_open` 与 `log:*` 事件换成可控输入），实测：

| 场景 | `scrollTop` / `scrollHeight` | 在底部 |
|---|---|---|
| 新建标签，边收边滚 | 5270 / 5874 | ✅ |
| 后台收了 300 行再切回来 | **0** / 5874 | ❌ |

**根因**：`TabHost` 用 `v-show` 隐藏非激活标签，`display:none` 时 `scrollHeight` 恒为 0，
后台收到的日志触发的 `el.scrollTop = el.scrollHeight` 全部无效（等于把位置写回顶部）；
而日志在后台一直流入，切回来时**没有任何补偿**，于是定在最上面；若构建已结束，就永远不再滚。

- [x] **Step 1: 抽出 `scrollToBottom()`，并对隐藏态设防**

```ts
async function scrollToBottom(): Promise<void> {
  if (!autoScroll.value) return;
  await nextTick();
  const el = outputRef.value;
  if (el && el.scrollHeight > 0) el.scrollTop = el.scrollHeight;  // 隐藏时别把位置丢回顶部
}
```

- [x] **Step 2: 切回标签时补滚**

```ts
const isActive = computed(() => tabs.activeId === props.tabId);
watch(isActive, (active) => { if (active) void scrollToBottom(); });
```

- [x] **Step 3: 回归验证**：同一探针重跑两场景，均在底部（5270 / 5874），修复前后对照明确。

- [x] **Step 4: 单测**（`src/views/LogView.test.ts`，新建）：新日志滚到底、关掉开关不跟随、
  隐藏时（`scrollHeight = 0`）不写滚动位置、切回标签时补滚到底。

> 为什么没上 ResizeObserver：另一个候选原因是进度行原地变长却不新增行——实测用
> 40 次增长的进度行（最长 302 字符）也填不满视口（内容高 604 = 容器高 604），
> 真正需要滚动的一定伴随新行，长度 watch 已足够；加 RO 只会多一份要维护的监听。

## Task 6: 日志「不实时更新」——根因是 `code=1` 的语义搞错了（用户实报）

**现象**：打开构建日志标签，只有打开那一刻的内容，之后不再更新、也不滚动。

**定位过程**（没有猜，全部有原始证据）：

1. 先看应用自己的留痕文件 `~/Library/Application Support/com.zhizhengroup.deploy/logs/`：
   - `auto/62891.log` 里有 **3 份** 递增的完整日志（75 / 113 / 147 行）；
   - `docker/148602.log` 里有 **4 份** 完全一样的完整日志（每份 1778 行）；
   - 结论：服务端每次推的是**全量快照**，而应用把每份都当增量追加了。
2. 新增诊断工具 `src-tauri/examples/probe_log_ws.rs`，直接连真实 `wss://…/wssapp/`
   打印**原始帧**，并且交叉验证「页面里的 `session_key`」与「cookie 里的 `sessionid`」——
   两者一致，认证帧没问题；帧长这样：

   ```
   #1 keys=["build_log","code"] build_log=87448B code=Some(1) msg=""
   （之后连接被直接 reset，没有 Close 帧）
   ```
3. 抓 ITSM 页面自己的客户端 `/static/js/myjs/build_log.js`（静态资源，无需登录）：

   ```js
   if (code == 0) { conn.close(); }                  // 0 = 错误，带 msg
   else if (code == 1) {
     $("#build_log").text(data["build_log"]);        // ← 全量覆盖，不是增量
     build_log.scrollTop = build_log.scrollHeight;
   }
   ```

**根因**：`code=1` 的含义是「这是一份新的全量日志快照」，页面靠反复收到它来刷新；
而实现把它当成了「日志已结束」，**收到第一帧就主动断开**，所以只看到一帧。
顺带两个同源问题：快照被当增量落盘（同一份日志写了很多遍）、服务端 reset 被当异常断开。

- [x] **Step 1: 修正 WS 语义**（`ws/log_socket.rs`）：`code=1` 不再结束；新增
  `StreamEnd { Complete, Closed, Rejected(msg) }`；`code=0` 把 `msg` 带出来；
  新增 `log_is_complete()` 按收尾行判定结束。
- [x] **Step 2: 只落盘/只推送增量**（`commands/log.rs`）：`snapshot_delta(known, snapshot)`
  → 增长取尾部、无新内容取空、对不上标记 `reset`；落盘基准从**已有文件内容**初始化
  （重开标签不会重复写）。
- [x] **Step 3: 重连策略**：有新增内容 → 500ms 后接着跟（重连是幂等的，增量会被比对掉）；
  没有新增 → 退避并计入重试。`code=0` 时若已有内容视为结束，否则报错并把服务端原话展示。
- [x] **Step 4: 前端**：`log://data` 增加 `reset`；`log://status` 增加 `detail`；
  store/ANSI 支持清空；日志页把服务端的原话显示在状态徒章旁边。
- [x] **Step 5: 验证**
  - Rust：`cargo test --lib` → **107 passed**（含 `code_1_is_a_snapshot_not_the_end`、
    `code_0_is_a_rejection_with_msg`、`snapshot_delta` 三条、收尾行判定）。
  - 真实服务端（用 `probe_log_ws` 的模拟模式跑**修复后的逻辑**）：
    - 已结束但仍有留存的 docker 任务 148602 → 「快照 87448B，新增 87448B，含收尾行 → 报已完成并停止」✅
    - 服务端已不留存的 auto 任务 62891 → 「服务端拒绝：数据格式错误（此前没有拿到内容）」✅
  - 前端：**215 passed**（含 reset 先清空再追加、服务端原话展示）。
- [ ] **待验证**：一次**真实进行中的构建**（端到端）：需实机提交一次部署观察。

> 另一个候选原因（也是真隐患）顺手修了：`App.vue` 的 `onMounted` 曾是一条 `await` 链，
> 链上任何一步抛异常，后面的 `registerLogEvents` 就不会执行 → 日志事件永远订阅不上且毫无提示。
> 现改为日志订阅提到最前、每步 `step()` 单独兜异常。

## Task 9: 批量部署（用户新增）与批次结算

**需求**：新增「批量部署」标签；同一环境一条分支一次提交多个项目；

**实现前发现的两个约束（都影响设计，写进 spec §5.7）**：

1. 提交接口只回 302、**不返回新建任务的 taskId** → 想让"整批一条通知"和"自动上线"知道是哪些任务，

- [x] **Step 2: 认领判据**：`taskId > baselineTaskId` + hash 前缀互配（列表里是纯 hash，
  提交时是 `hash#-----#message`）+ 分支一致（列表拿不到分支时跳过该条，不否掉候选）。
- [x] **Step 3: 汇总与抑制**：整批到终态发一条（`N 个任务全部结束（X 成功 / Y 失败）`，

  超时（30 分钟）兜底：已认领到过就汇总已有结果，一个都没认领到就作废（没抑制过东西）。
- [x] **Step 4: 自动上线**（`beginOnline` 防重复）：只在 `构建成功` 且开关打开时调 `submitOnline`，
  失败不阻塞后续；汇总里带"已自动上线 N 个"。
- [x] **Step 5: 通知统一出口**（`lib/notify.ts`）：权限申请与「要不要打扰用户」的判断只有一份，
  逐条通知与汇总通知共用（否则两个发送方迟早出现"一个遵守设置、一个不听"）。
  顺带把 `terminalState / wasBuilding` 抽到 `lib/taskStatus.ts`（两处共用）。
- [x] **Step 6: 界面**（`views/BatchDeployView.vue`）：多选项目 → 分支下拉（并集 + 覆盖度）

- [x] **Step 7: 接线**：`TabKind` 加 `batch`（单例）、侧栏导航项、`Cmd+2`（顺序变 1..6）、TabHost。
- [x] **Step 8: 测试**：批次 store 6 条（认领/baseline/汇总一条/自动上线只在成功后且只一次/开关关闭绝不上线/
  超时兜底）；通知层 2 条（批次内抑制、批次外照常）；批量页 5 条（分支并集与覆盖度、
  分支不存在跳过、串行提交 + 开批次、部分失败不算进批次、开关默认关+警告）。

## Task 13: 日志显示优化（语法高亮 / 查找 / `$<3>` 还原）

**先看真实字节**（本机留存文件）：

ESC[1A ESC[1K $<3> ESC[K $<3> \r 127bb7ebb685: Preparing ESC[1B
